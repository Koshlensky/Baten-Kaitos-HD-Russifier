# RE-проба GameAssembly.dll: можно ли восстановить говорящих

## Коротко

За время пробы говорящих восстановить не удалось, критерий «80% реплик в двух сценах» не выполнен. Причина — архитектура, а не нехватка инструментов: ремастер эмулирует исходную скриптовую машину GameCube, и функция вывода реплики не получает идентификатор говорящего. Облачко ставится в экранные координаты модели персонажа, вычисленные во время выполнения.

Технически извлечение, вероятно, частично возможно, но это многодневный реверс-инжиниринг: распаковка байткода, дизассемблер скриптовой машины, отслеживание аргументов позиции окна до модели персонажа и сопоставление моделей с персонажами. По условиям пробы без согласования это не начинается. Ниже — что найдено, оценка и альтернатива.

Попутно найден механизм, важный для рода: BK1 умеет спрашивать пол духа-хранителя и хранит для его реплик мужской и женский варианты.

## Условия

- Лимит 30–60 минут; уложились (начало в 16:07 по системным часам).
- Только копии: `work/re/bk1|bk2/GameAssembly.dll` и `global-metadata.dat`, скопированы с проверкой SHA-256. Файлы игры не изменялись.
- Инструменты: Il2CppDumper v6.7.46 (net6-win, источник и хеш — в `tools/third_party/README.md`), capstone 5 для дизассемблирования x64. Скрипты — в [`tools/re/`](../tools/re/README.md).

## Что найдено

### 1. Метаданные читаются полностью

Метаданные и IL2CPP версии 29. Il2CppDumper выдал `dump.cs` (сигнатуры всех классов с RVA), `script.json`, `stringliteral.json`, `il2cpp.h`.

### 2. Сцены — эмуляция скриптов GameCube

Для каждого исходного файла скрипта есть пара классов (имена по ID файла оригинала):

- `LB.PRJ0505.Batenkaitos1.ScriptCode_E000505E : ScriptCode` — статические массивы `opCodeDatas` (сжатый байткод), `codeAddrTable`, `resourceAddrTable`;
- `ScriptResource_E000505E : ScriptResourcePack` — статические буферы `buffer_0x2060f3e0…`, названные по адресам памяти GameCube.

Общий движок — `LB.PRJ0505.Common`:

- `ScriptProcess` — стековая машина, перечисление `OPCODE` (~140 инструкций: `OP_IMB`, `OP_LDW`, `OP_JZ`, `OP_CALL`, `OP_CALS`, `OP_PUSH`…), чтение операндов `opr8/16/32/64`;
- `SystemFunctionsBase` — 267 системных функций, вызываемых скриптом по индексу; в BK1 их дополняет `SystemFunctions`;
- `ScriptCode.decompressCode` пропускает 18-байтовый заголовок и читает сжатый поток (по виду — стандартный Deflate).

### 3. Реплики в скриптах заменены маркерами ID

В ресурсах скриптов исходный текст заменён строками `@@ID@@`; `MessageConverter.convertTextID2Text` подставляет вместо них текст из `TextManager`.

- BK1: 10 060 маркеров (из них `SCR_*` — 9 685, `NPC_*` — 176, `KYO_*` — 73, `MGN_*` — 72).
- BK2: 14 914 маркеров (`EV_*` — 4 124 из 4 233, `MINTAKA_*` — 884, `SHERATAN_*` — 759, …, `NPCName_*` — 307).

Значит, связь «ID текста → файл скрипта» восстанавливается статически. Для BK2 это дало бы точные границы сцен вместо эвристики.

### 4. Как выводится реплика

Системные функции окна: `_CreateWindow`, `_SetOpenPos`, `_SetWindowPos`, `_OpenWindow`, `_Print`, `_IsPrinting`, `_SetFace`, `_ReadFace`, `_SetNameTag`, `_ReadVoice`, `_PlayVoice`; позиция — `SF_CalcScreenPosition` и `_GetScreenPosition`. У класса `Window` есть `faceImage`, `namePlate`, `nameText`, `setNameText()`; `WindowManager.create(type, x, y, …)` создаёт окно по экранным координатам.

Вывод: `_Print` печатает ресурс без указания говорящего. Говорящий задан неявно — через координаты модели, к которой привязано облачко. Явная подпись возможна только через `_SetNameTag` (табличка с именем) и `_SetFace` (портрет). Скрипты ссылаются на имена NPC (`NPC_*`, `NPCName_*`) — вероятно, это и есть таблички (гипотеза, не проверена).

### 5. Выбор пола духа-хранителя (BK1)

- Экран ввода имени `NameInput` содержит состояние `GenderSelect`, значения `Man`/`Woman` и строки `genderSelectTextId`, `genderManTextId`, `genderWomanTextId`. Текст вопроса — `SYS_0227` «Please select your gender.».
- `TextManager.isEnabledSelectGender()` (дизассемблировано) возвращает true только для языков `jp` (0), `kr` (13), `tc` (11), `sc` (12). Для `en` (1) и `ru` (7) вопрос не задаётся.
- В BK1 154 меню выбора (реплики самого духа) имеют варианты с суффиксами `_0` и `_1`. В японском `_0` — женская речь («そうね！いらないわ», «当たり前よ»), `_1` — мужская («そうしよう！いらないよ», «当たり前さ»). В английском варианты совпадают в 108 парах из 154.
- Какой вариант игра показывает при выключенном выборе пола (слоты EN и RU), не установлено.
- В BK2 выбора пола нет; в титрах есть «Guillo (Male)» и «Guillo (Female)» — два голоса Гилло.

Следствие для перевода: реплики духа в этих 154 меню можно перевести в обоих родах. Нужно решить, как сделать вариант видимым русскому игроку (см. [DECISIONS.md](DECISIONS.md)).

## Вердикт по критерию

Критерий пробы («в двух сценах говорящий восстанавливается из кода у ≥80% реплик и не противоречит японским уликам») **не выполнен**. Причина — говорящий не хранится рядом с репликой, а вычисляется из данных о позиции во время выполнения.

## Оценка полного извлечения

**Этап A (1–1,5 дня), ограниченный и с понятным результатом:**

1. Разбор таблицы данных статических массивов в метаданных, извлечение `opCodeDatas` и буферов ресурсов.
2. Распаковка байткода (Deflate после 18-байтового заголовка).
3. Дизассемблер скриптовой машины (форматы операндов — из интерпретатора `ScriptProcess`).
4. Карта «ID текста → файл скрипта, функция, смещение», поиск вызовов `_SetNameTag` и `_SetFace` рядом с `_Print`.

Что даст: точные границы сцен BK2; проверку схемы ID BK1; явные подписи NPC там, где используются таблички; список мест с портретами. Говорящих в катсценах этап A не даст.

**Этап B (2–4 дня), с высокой неопределённостью:** отслеживание аргументов `_SetOpenPos`/`_SetWindowPos` до `SF_CalcScreenPosition(персонаж)` и далее до `SF_CreateChar(модель)` или `_GetNpcId`; таблица «модель → персонаж» (частично вручную). Что даст: говорящих в катсценах — там, где позиция окна вычисляется от персонажа, а не задана константой.

## Альтернатива без масштабного реверса

1. Улики из параллельных текстов: японская речь (местоимения, окончания, вежливость), в BK1 — родовые формы французского, испанского, итальянского, немецкого; обращения по имени и чередование реплик в английском. Прототип — `tools/bkloc/evidence.py`.
2. Разметчик (Claude Opus) по сцене с уликами выставляет говорящего и уверенность; спорное получает статус `needs_context`.
3. Ручная проверка критичных строк по прохождениям и видео — там, где от говорящего зависит род в русском.

## Рекомендация

Согласовать только этап A: он ограничен по времени и даёт измеримую пользу (точные сцены BK2, подписи NPC, проверка схемы ID). Решение по этапу B принимать по итогам этапа A. До согласования пайплайн работает по альтернативному пути — он нужен в любом случае, потому что даже этап B не покроет все реплики.
