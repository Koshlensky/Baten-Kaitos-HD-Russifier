# Этап A реверс-инжиниринга: говорящие и порядок реплик из скриптов игры

Разрешён решением D-016. Работа велась только с копиями `GameAssembly.dll` и `global-metadata.dat` в `work/re/<игра>/`; файлы установленной игры не менялись. Инструменты — `tools/re/`, команды воспроизведения — в [tools/re/README.md](../tools/re/README.md).

## Итог

**Говорящий у большинства реплик восстанавливается из данных самой игры.** Ремастер показывает над окном диалога табличку с именем говорящего. Имя передаётся в скриптовую машину вместе с репликой, и его можно извлечь без запуска игры.

| | BK1 | BK2 |
|---|---:|---:|
| Сюжетных строк (диалоги) | 9 991 | 14 669 |
| Табличка имени (однозначно) | 5 806 | 8 901 |
| Продолжение окна того же актёра (вывод) | 15 | 80 |
| Окно без таблички | 2 790 | 3 347 |
| Меню выбора | 371 | 659 |
| Подписи (названия предметов, пункты) | 399 | 273 |
| Одна строка у разных говорящих | 60 | 63 |
| Имя вычисляется во время игры | 69 | 61 |
| Не найдено в вызовах | 481 | 1 285 |

Кроме того, у 54 записей дневника BK2 (сводки сюжета) табличка указывает автора: «Sagi's Journal», «Guillo's Journal», «Milly's Journal».

Проверка на пилотных сценах (54 строки, ручная разметка из `base/evidence/pilot_expected.json`):
- все строки, где я была уверена, совпали с табличками, кроме одной;
- эту одну (`SCR_EVE08_2_2936`, «[…]...») я приписала Georg, а табличка указывает Larikush, и по смыслу права игра: это учёный, который отвечает за рост Kalas;
- 7 строк, которые я пометила как сомнительные или неизвестные, получили говорящего; в одном случае (`SCR_EVE08_2_2349`) табличка опровергла мою догадку.

Вывод: контекстная разметка без данных ошибается даже на коротких сценах, а табличка — это то, что игра показывает игроку.

## Что установлено

### Данные скриптов
- Каждый файл скрипта GameCube хранится в двух классах IL2CPP: `ScriptCode_<fileId>` (байткод) и `ScriptResource_<fileId>` (данные).
- Массивы заполняются в статических конструкторах через `InitializeArray`. Привязка массива к полю делается по смещению записи в структуре статических полей.
- Поля `ScriptResource` называются по адресу GameCube (`buffer_0x20178e60`). Текстовые буферы содержат маркер `@@ID@@` — ключ строки в `TextData_<язык>`.
- Часть полей — пустые массивы без `InitializeArray`: 619 в BK1, 524 в BK2. Из-за них простое сопоставление «по порядку» сдвигалось, и это была ошибка первой версии `script_data.py`.
- Итого: BK1 — 556 файлов и 81 806 маркеров, BK2 — 1 283 файла и 22 168 маркеров. Число полей совпадает с объявленным во всех классах.

### Байткод
- `opCodeDatas`: 16 байт заголовка (байты 4–7 — размер распакованного кода), затем zlib.
- `codeAddrTable` и `resourceAddrTable` — таблицы перемещений: дельты `ushort` к позициям 4-байтовых адресов кода и адресов буферов ресурсов.
- Стековая машина `ScriptProcess`: 139 опкодов, операнды big-endian фиксированной длины. Длины сверены вручную по обработчикам `runOpCodes` (`tools/re/vm_disasm.py`).
- В BK2 байты опкодов начиная с `0x7E` на единицу меньше: `ScriptProcess.getOpCodes` в BK2 прибавляет 1. После этой поправки разбор BK2 так же точен, как BK1.
- Проверка разбора: позиции из таблиц перемещений приходятся на операнды команд. В BK1 это 99,3% адресов кода и 99,9% адресов ресурсов, в BK2 — 99,6% и 99,99% при линейном разборе. Остальное выравнивается по якорям из тех же таблиц.
- Системные функции (`SystemFunctions..cctor`, записи `FunctionData(номер, имя)`): в BK1 два режима (197 и 153 функции), в BK2 — 653 записи.
  - BK1: `_Print` = 44, `_SetFace` = 46, `_SetNameTag` = 70.
  - BK2: `_Print` = 209, `_SetFace` = 211, `_SetNameTag` = 215.

### Как выводится реплика
Разобрано на BK1 (EVE08, файл `E00050FB`), затем подтверждено на всех файлах обеих игр:

1. Скрипт вызывает локальную функцию реплики с аргументами `(окно, …, ID озвучки, РЕПЛИКА, ИМЯ, флаги, …, актёр)`.
2. Функция запускает процесс. Процесс через функцию настройки окна вызывает `_SetNameTag(окно, ИМЯ)`, затем `_Print(окно, РЕПЛИКА)` и воспроизводит озвучку.
3. Перед вызовом `_SetNameTag` в коде стоит блок `NOP`: похоже, ремастер вырезал часть оригинального кода и вставил табличку на её место.
4. Имя — текстовый ресурс: `PCN_*`, `NPC_*`, `MGN_*`, иногда `SCR_*` в BK1 и строки локаций, `NPCName_*`, `CMP_DATA_*` в BK2. Значение 0 на месте имени означает окно без таблички (3 300 вызовов в BK1).
5. Каждый файл держит свои копии библиотечных функций. Функция опознаётся по отпечатку тела (байткод до первого `OP_RET` с замаскированными адресами). 14 библиотечных функций в BK1 и 20 в BK2 дают базовые сигнатуры.
6. Обёртки (функции, которые передают свои аргументы или константу дальше) получают сигнатуру автоматически: в BK1 их 2 559, в BK2 — 1 544. Например, обёртка с 7 аргументами всегда подставляет 0 на место имени.
7. В BK2 продолжение реплики выводится отдельной функцией без имени, с тем же номером актёра. Такие строки помечаются как вывод (`inferred`), а не факт.

### Что ещё видно в данных
- **Общие строки.** 60 строк BK1 и 63 строки BK2 вызываются с разными табличками: «Yeah.», «......», «What?», «Squeak.». В BK1 строка «What do you say, `<n0>`?» звучит то у Kalas, то у Xelha. Перевод таких строк должен подходить всем говорящим, без рода. Это отмечено в матрице (`speaker.status = needs_context`) и в контексте строки.
- **Неопознанный говорящий.** Табличка «？» (`GRP_156`) — игра намеренно скрывает имя.
- **Обобщённые таблички.** «Male» (`NPC_185`), «Woman with a Bracelet», «Imperial Soldier» и т.п. Иногда они дают пол безымянного персонажа, но решение о роде принимается по контексту, а не только по табличке.
- **Меню выбора с вариантами `_0`/`_1`** (реплики духа-хранителя в BK1). В функцию меню передаются оба варианта; выбор делается внутри процесса во время игры. Этот выбор я не трассировала: по D-003 проверка — в игре на пилоте.
- **Озвучка.** Аргумент перед репликой — ID голосового файла (`0x6000xxxx`), он сохранён в `base/evidence/<игра>_script_speakers.jsonl` (`voices`).

## Результаты в проекте
- `base/evidence/bk1_script_speakers.jsonl`, `bk2_script_speakers.jsonl` — для каждой сюжетной строки: статус, имена с табличек и число вызовов, ID озвучки, файлы скриптов.
- `base/scenes/<игра>_script_sequences.json` — реплики каждого файла скрипта в порядке кода, с говорящим. Это настоящий порядок строк внутри сцены (с оговоркой о ветвлениях ниже).
- `base/scenes/<игра>_script_files.json` — карта «строка → файл скрипта» для обеих игр. BK2 теперь группируется по сценам точно: реплики событий разложены по 285 файлам.
- Матрица: `speaker.status = confirmed_data` и `speaker.name_tag` для строк с табличкой; `needs_context` для общих строк; `inferred` для продолжений. Ручная разметка разметчика при пересборке сохраняется (`speaker.source = annotator`). В пакеты переводчика и редактора добавлено английское имя с таблички.

## Ограничения
- Табличка — это имя, которое видит игрок. Она не определяет грамматический род и не заменяет литературную проверку. Род по-прежнему решается по карточке персонажа и правилам [06_gender_rules.md](06_gender_rules.md).
- Адресат в данных не закодирован. Аргументы `10000+n` в вызове реплики похожи на цели камеры или взгляда, но это не проверено.
- У окон без таблички (описания при осмотре, мысли, безымянные NPC) говорящий из данных не следует. Номер актёра указывает на объект сцены, но чтобы связать его с персонажем, нужен разбор `SF_CreateChar` — это не делалось.
- Порядок в коде совпадает с порядком в игре для линейных сцен. Ветвления (условные реплики, повторные разговоры) делают его нелинейным.
- Около 1 800 строк (BK1 + BK2) не найдены в вызовах. Это строки, на которые нет прямых ссылок из кода (возможно, неиспользуемые), и вызовы, не попавшие под известные сигнатуры.

## Решение об остановке
Задача этапа A выполнена: говорящие, порядок и группировка по сценам восстановлены для обеих игр. Дальнейшие направления полезны, но это уже новый объём работ, и без согласования я его не начинаю:
1. связь номера актёра с персонажем для окон без таблички;
2. адресат по целям взгляда или камеры;
3. выбор варианта `_0`/`_1` во время игры (D-003).
